# HTTP 接続のトラブルシューティング

## 今回確認できた現象

| 状態 | 外部ブラウザ | 内部 curl |
| --- | --- | --- |
| 通常時 | success | 200 |
| Security Group の HTTP 80 遮断試験 | timeout | 200 |
| HTTP 80 復旧後 | success と報告 | 再測定値は未報告 |

HTTP 80 復旧の success は利用者の報告です。復旧後のブラウザ画面や生ログはこの記録に含まれません。

## 解釈

内部 HTTP 応答が維持されたため、試験時に Web サービスが全面停止していたという説明とは整合しません。ルール復旧後の成功も含めると、Security Group による外部到達性の制御と整合する結果です。ただし、内部 curl の宛先は不明であり、NACL・ルート・OS ファイアウォールを個別に検証した記録はありません。timeout 単独から原因を断定しません。

## 再発時の切り分け手順（未実施の提案）

1. 同じホスト・URL・HTTP ポートで比較しているか確認する。再起動後はパブリック IPv4 の変更にも注意する。
2. EC2 内で `systemctl is-active nginx`、`sudo nginx -t`、`sudo ss -lntp` を確認する。
3. `curl -sS -o /dev/null -w '%{http_code}\n' --max-time 10 http://127.0.0.1/` でローカル応答を確認する。
4. 対象 EC2 に関連付くすべての Security Group と HTTP 80 の送信元を確認する。複数グループの許可は合算されるため、別ルールで許可されていないか確認する。
5. 解消しなければ、パブリック IP、Internet Gateway への経路、NACL、OS ファイアウォール、Nginx の待受アドレスを順に確認する。
6. HTTP 403/404/5xx が返る場合は、timeout と区別し、Nginx 設定やコンテンツ、ログを確認する。

確認ログはまず非公開で保管し、公開時には IP、識別子、認証情報を除去してください。
